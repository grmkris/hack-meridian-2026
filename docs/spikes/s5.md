# S5 · Integration: the pocket model end to end: results

Status: **done, claims 1–8 PASS**, 2026-10-25 12:01–12:20 UTC on Stellar testnet (protocol 29). Author: S5 spike agent.

## Question

Does the full pocket model work end to end with the real smart account and rule from S1 and the real seller and hosted
facilitators from S2? And what does the build need to know about fees, chunking, idempotency and sweep?

**Answer: yes, with no new library code.** S1's connection key `K` pulled from S1's account `CD4B4YAP…A753` under rule 4
(`s5-grant`, 5 USDC) into its own sponsored pocket `G(K)` (0 XLM). The stock `@x402/stellar` client then paid S2's seller
from the pocket, over HTTP through x402.org and over MCP through OpenZeppelin Channels.

- The policy view moved by exactly each pull.
- Over-budget pulls were refused at the enforce simulation with `#3221`, and the facilitator was never called.
- A replayed idempotency key returned the first receipt with no pull and no payment.
- Revoke removed the rule, the next pull was refused with `#3000`, and the pocket was swept and closed.

**The one number that matters: each pull costs about 1.69 XLM of rent, whatever the amount.** The first pull of a grant
costs 12.26 XLM. The x402 settlement costs us nothing, because the facilitator pays its 0.0023 XLM. The rent is per
policy history entry, not per USDC, so **chunking is the lever**: one 1.00 USDC pull served three 0.10 purchases for the
price of one pull.

## What happened

### Claim 1 · Pocket for S1's `K`

`G(K)` already existed: S1 had friendbot-funded it with **9,999.99999 XLM** and a USDC trustline, and it held 8.10 USDC
from S1's pulls. S5 reused the key and converted the account to the product shape:

1. **Return S1's leftover 8.10 USDC to the smart account** with a Soroban SAC `transfer(G(K) → C)`. The relayer is the
   source and `K` signs only the address auth entry:
   [`ccdf083d`](https://stellar.expert/explorer/testnet/tx/ccdf083d15d6708b46b549467a617b8306e6301c2282b29601d8e709e99b4368)
   (21,921 stroops).
2. **Merge** `G(K)` into the relayer (`ChangeTrust` limit 0 + `AccountMerge`):
   [`95920d73`](https://stellar.expert/explorer/testnet/tx/95920d7338be1b885364f47b5589151f8b81dccff10fbe382a69fe0da9785124)
   (200 stroops).
3. **Recreate** it with relayer-sponsored reserves (`BeginSponsoring` → `CreateAccount(0)` → `ChangeTrust(USDC)` →
   `EndSponsoring`):
   [`b0c22b38`](https://stellar.expert/explorer/testnet/tx/b0c22b384fcf49fe444bf8fdc38bf4cbaf58f63255b3481efcd6ed7b2a4e94f2)
   (400 stroops, 4.8 s).

Afterwards `G(K)` held **0 XLM**, 0 USDC, `num_sponsored` 3, sponsored by the S5 relayer, whose `num_sponsoring` was 3.
That is 1.5 XLM of the relayer's minimum balance, recoverable.

Why it costs that much (`out/rent-anatomy.txt`, `src/tools/rent.ts`):

- **Every later pull appends one 80-byte `SpendingEntry`** to the policy's `AccountContext` entry (384 → 464 B). Rent
  for those 80 B is prepaid for the entry's remaining ~30-day TTL.
- **The first pull also extends two entries** from 7 to 30 days, +397,610 ledgers each: the policy's 384-byte
  `AccountContext` and the account's `ContextRuleData(4)`.
- **Testnet rent is at 52.5× the at-target rate right now.** Live Soroban state is 4,015,269,406 B, 0.382 % over the
  4 GB target, so the write fee is 525,447 stroops/KB against 10,000 at target. An hour earlier, at S1's measurement,
  it was 47×. Formula and code are from S1's "Fee anatomy".
- **The amount does not matter, only the number of pulls.** At the at-target rate a later pull would cost ≈ 0.034 XLM.
- **The enforce simulation's declared fee is 1.15× the charge** (the rest is refunded). The record-mode `minResourceFee`
  is useless as an estimate: 52.5M for every pull, and 55.4M for a 22k-stroop sweep.

## Recommendation for the build

### The exact sequence `paid_resource_fetch(url, idempotency_key)` must run

This is `spikes/s5/src/intents.ts`, with the store moved into the Durable Object:

1. **Intent lookup** in the Durable Object by `(connection, idempotency_key)`, before any network call.
   - If it exists with the same fingerprint (method + URL; for MCP, server + tool + args), return it: the receipt if
     `confirmed`, the state otherwise. **Never re-run it.**
   - The same key with a different fingerprint is a conflict.
   - Otherwise persist a new intent as `prepared`.
2. **Unpaid request.** If the answer is not 402, return the content. On 402 the stock client parses `PAYMENT-REQUIRED`
   (HTTP) or the `PaymentRequired` tool result (MCP).
3. **`onBeforePaymentCreation` = the grant hook** (one hook for both transports):
   1. Validate: scheme `exact`, network `stellar:testnet`, asset = USDC SAC. `setSpendControls({ maxAmountPerPayment })`
      is the per-payment belt.
   2. `float` = `G(K)`'s USDC balance (SAC `balance`); `remaining` = `spending_limit − cached_total_spent` from
      `get_spending_limit_data`, minus what other in-flight intents have reserved.
   3. If `float + remaining < price`, return `{ abort: true }` and mark the intent `requires_approval` (owner lane).
      Nothing is signed and the facilitator is never called.
   4. Otherwise reserve `price`. `pull = float ≥ price ? 0 : min(remaining, max(price − float, CHUNK))`.
4. **Pull** (if `pull > 0`): persist `pulling`, then run S1's flow: record sim → `authorizeEntry` with `K` under the
   rule id → **enforce sim** → assemble → relayer signs → send → poll.
   - If the enforce simulation fails, **never submit**. Map `#3221` → `requires_approval`, `#3000` → revoked,
     `#3002` → expired.
   - Persist the pull hash, ledger and fee.
5. **Pay**: persist `paying`. The stock `ExactStellarScheme(createEd25519Signer(K))` signs as `G(K)`. Attach
   `payment-identifier` = intent id and retry.
6. **Receipt only on `success`**: `getPaymentSettleResponse` (HTTP) or `paymentResponse` (MCP).
   - On success: `confirmed`, consume the reservation, and return
     `{ pull: {tx, ledger, fee}, settlement: {tx, payer: G(K), facilitator}, grant_remaining: policy remaining + float }`.
   - On failure: `failed`, release the reservation. The float stays in `G(K)` and is still spendable.

Measured: the service pre-check costs 0.5–0.9 s, because it runs two RPC simulations. Cache the policy view in the
Durable Object and update it from each pull's result.

### Chunk policy

- **Pull `min(remaining, max(shortfall, CHUNK))` with `CHUNK = 1.00 USDC`** (10 purchases at $0.10).
- Each pull costs 1.69 XLM whatever its size, so this cuts relayer rent per purchase about 10×. It also makes 9 of 10
  purchases skip the 4–8 s pull, leaving 5–8 s instead of 10–13 s.
- It also stretches the policy's 1,000-entry history cap (`#3224`) to 10,000 purchases per grant.
- A float adds no exposure: `K` can already pull everything that remains.
- Show the agent and the owner **remaining = policy remaining + float**, and **spent = sum of settled receipts**, not
  the policy's `cached_total_spent`.
- On revoke **and on expiry**, sweep the float back. Expiry has no transaction, so schedule the sweep.
- For a demo narration that wants the onchain `spent` to equal purchases, `CHUNK = 0` (exact) also works: on testnet the
  rent is friendbot money.

### Where idempotency lives

**In our intent store, keyed by idempotency key, checked before the 402 negotiation.** Two backstops sit behind it:

- The shortfall rule makes a retried pull self-limiting: a pull that landed leaves `float ≥ price`, so a retry does not
  pull again. This is a design property, not exercised by a crash test here.
- The intent id as the x402 `payment-identifier` lets sellers that cache (ours do) return the first receipt.

A signed payload that never settled is live for about 12 ledgers (`maxTimeoutSeconds` 60). Do not re-sign an intent in
`paying` until that window has passed.

### Relayer funding rule

Testnet costs at today's rent (52.5× at-target), per connection grant:

| Item                                          | XLM                                              |
| --------------------------------------------- | ------------------------------------------------ |
| pocket reserves (sponsored, locked)           | 1.5, returned on close                           |
| grant install (owner op)                      | 2.9 (S1: 3–14; 13.8 for an account's first rule) |
| first pull of the grant                       | 12.3                                             |
| each further pull or direct delegated payment | 1.7                                              |
| revoke + sweep + close                        | 0.005                                            |
| x402 settlements                              | 0 (the facilitator pays)                         |

**Rule: hold 50 XLM per connection per day plus 1.5 XLM locked per open pocket. Alert below 500 XLM and top up from
friendbot.** For example, 20 purchases a day costs 1.5 + 2.9 + 12.3 + 19 × 1.7 ≈ 49 XLM in exact mode, or about 18 XLM
with 1-USDC chunks. A 5-USDC grant with 1-USDC chunks needs at most 5 pulls, so ≤ 23 XLM for its whole life.

Also budget the shared-contract TTL extension (open risk 1). One friendbot account (10,000 XLM) covers about 200
connection-days.

### Fee ceiling per intent

Use the **enforce simulation's** fee. It is the declared fee, about 1.15× the charge.

- Refuse a pull above **3 XLM**, or **20 XLM** when it is the grant's first spend (the policy's TTL is due).
- Report `fee_ceiling_exceeded` and never submit.
- The settlement leg needs no ceiling of ours: the facilitator pays it (22,771 stroops, under OZ's 1M cap and
  x402.org's ~50k).
- Make both numbers config: they track testnet state size, and at the at-target rate they would be about 0.05 and
  0.4 XLM.

## Open risks

1. **The shared spending-limit policy expires during judging.** Its instance and its 14,808-byte WASM
   (`e41b563c4454f5a6742acfa6d44e1ece96d443bb5f40efddd6ed05180210219a`, contract `CABXBYJN…TIP5G`) live until ledger
   **5,408,831**, about **27 Oct 02:30 UTC** (38 h after this run; `out/shared-ttl.json`).
   - Nobody extends them: the policy does not extend its own instance.
   - After that, every delegated pull or payment needs a restore first, paid by whoever transacts. The restore runs
     either through the simulation's archived-entries footprint or as a `RestoreFootprint` op; neither was verified
     here. At today's rate it costs about 76 XLM for 7 days of WASM rent, which breaks any sane fee ceiling.
   - **The build's relayer must run `ExtendFootprintTTL` on the policy instance and WASM before the deadline**, for
     example `stellar contract extend --id CABXBYJNZ7IUW4G3D6BND5YCAQF3ASSDMDAOKQQ63UYFSO7WUU2TIP5G --ledgers-to-extend 120960 --durability persistent`
     plus the same with `--wasm-hash e41b563c…`. That costs about 76 XLM per 7 days at 52×.
   - The account WASM (145 days), the Ed25519 verifier (25 days) and the USDC SAC are fine. Each new account's
     instance lasts about 7 days.
2. **Testnet rent keeps rising**: 47× → 52.5× at-target within an hour, so 1.58 → 1.69 XLM per pull. The fee ceiling
   must be config, and the relayer balance must be watched. Mainnet at or under target would be about 50× cheaper.
3. **Pulled float is "spent" onchain.** The policy counts it at pull time. UIs that read `cached_total_spent` directly
   will show less allowance than the agent really has. Expiry needs a scheduled sweep.
4. **The first spend of every grant costs about 12 XLM** of TTL extension, prepaying 30 days for a 1-day grant. That is
   a constant of the OpenZeppelin policy. Only a custom policy (running total, no history) avoids it, which is
   post-hackathon.
5. **Latency**: exact-mode purchases take 9.8–13.0 s, chunk hits 5.3–7.9 s. The facilitator's settle (3.3–6.6 s) is the
   floor. Hosts must not time out under 15 s.
6. **Not tested here**: concurrent intents on one relayer (sequence contention), crash recovery mid-`paying`, workerd.
   The in-memory store is single-process. The build moves it into the Durable Object, which serializes reservations.
7. **S1's connection pocket is gone.** `G(K)` for `GCEM4WKC…` was merged, recreated sponsored by the S5 relayer, then
   closed, and rule 4 was removed. The account `CD4B4YAP…` now holds 19.75 USDC. Use S1's
   `bun src/tools/s5-grant.ts <C>` for a fresh grant, and S5's `createSponsored(K)` for a fresh pocket.
