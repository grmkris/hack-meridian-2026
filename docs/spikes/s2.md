# S2 · x402 on Stellar, end to end: results

Status: claims 1–4 **PASS**; claim 5 (as re-scoped at 11:48 UTC) **PASS**. Run 2026-10-25 11:38–12:00 UTC on Stellar
testnet (protocol 29). Author: S2 spike agent.

## Question

Can our own code pay a Stellar x402 seller on testnet and get a receipt back? Does x402 over MCP work with the Stellar
scheme? And how do we pay from the smart account's budget when the hosted facilitators reject contract-account payers?

**Answer: yes to all three, with the stock libraries and no fork.**

- `@x402/stellar` 2.28.0 paid our Bun seller and the public Stellar demo seller from a classic `G…` account.
- `@x402/mcp` 2.28.0 paid an MCP tool over Streamable HTTP on MCP SDK 1.32.2, with no `-32042` workaround.
- Both hosted facilitators settled: x402.org (no key) and OpenZeppelin Channels (free testnet key).

Re-scoped claim 5 is the **pocket model**. The connection key `K` signs on the smart account's spending-limit rule and is
also the key of its own classic account `G(K)`. For each purchase, `K` first pulls the price from the smart account into
`G(K)`. Then `G(K)` pays the seller with the stock client through a hosted facilitator. `G(K)` holds 0 XLM because the
relayer sponsors its reserves.

### 2. Classic payer, receipt, dedup (claim 2)

`client/pay.ts` chains `createEd25519Signer(PAYER)`, `new x402Client().register("stellar:*", new ExactStellarScheme(signer, {url}))`
and `wrapFetchWithPayment(fetch, client)`. It reads the receipt with
`new x402HTTPClient(client).getPaymentSettleResponse(h => res.headers.get(h))`.

- **First payment**: 200 in 7.7 s. Settle response
  `{"success":true,"payer":"GBALHRKN…VFCB","transaction":"5dfcdaa0…","network":"stellar:testnet"}`, tx
  [5dfcdaa0…](https://stellar.expert/explorer/testnet/tx/5dfcdaa07d2e535ca6d4729f97b51d24c2ecb1dfbb7fec052c5fe8ca62a09e1f).
  The fee was 21,155 stroops (max 27,679). The tx source was x402.org signer `GC6CSXBV…`, fee-bumped by the second signer
  `GC5OLUZ4…`. The seller logged verify in 627 ms and settle in 5,633 ms.
- **Payment identifier.** The client takes `generatePaymentId()` (or a fixed id) and calls
  `appendPaymentIdentifierToExtensions(ctx.paymentRequired.extensions, id)` in `onBeforePaymentCreation`. The seller
  declares `declarePaymentIdentifierExtension(false)` and registers `paymentIdentifierResourceServerExtension`.
  - **The 2.28.0 middleware does not cache.** The server extension object is just `{ key }`, with the comment "Future hooks
    for idempotency could be added here". The cache is ours: an outer Hono middleware decodes `PAYMENT-SIGNATURE` with
    `decodePaymentSignatureHeader` and calls `extractPaymentIdentifier`.
  - The cache is keyed by id and bound to a fingerprint `[scheme, network, asset, amount, payTo, method, path]`, as the
    spec requires.
  - On a hit it returns the stored 200 body and the `PAYMENT-RESPONSE` header without calling the facilitator. The same
    id with a different fingerprint returns 409.
  - Id `pay_s2_dedup_1792928614_abcdef`, call 1: settled
    [792a6ec4…](https://stellar.expert/explorer/testnet/tx/792a6ec4e739602a53c76aff3a26aa74a9b3cd7704a2dcd7373d71e0f1061710)
    in 8.3 s.
  - Same id, call 2: **200 in 984 ms, `x-s2-cache: hit`**. It returned the same body (`"served":2`, so the handler did
    not run again) and the same receipt tx `792a6ec4…`. The seller logged
    `payment-identifier …: cache hit, no verify/settle`. The client still signed a new payload, which was never settled
    (see risks).
  - Replaying the first raw `PAYMENT-SIGNATURE` header with curl also got 200 and a cache hit.
- **A payload cannot settle twice.** The consumed payload went straight to x402.org: `/verify` returned
  `{"isValid":false,"invalidReason":"invalid_exact_stellar_payload_simulation_failed"}` and `/settle` returned
  `{"success":false,"errorReason":"invalid_exact_stellar_payload_simulation_failed","transaction":""}`.
  - The cause shows in a local simulation of the same payload. It was run before the scope change removed that code. Fresh
    payment
    [295f65bc…](https://stellar.expert/explorer/testnet/tx/295f65bc25644a8c47ff6472006003ccf76220fbef7538ad9244bfe61a76c806),
    replayed within its expiry window, failed with
    `HostError: Error(Auth, ExistingValue)` … `["nonce already exists for address", GBALHRKN…]`.
  - So the auth-entry nonce is consumed onchain, and x402.org reports only the generic reason.

### 4. x402 over MCP with the Stellar scheme (claim 4)

The server is `mcp/server.ts`: `McpServer` plus `WebStandardStreamableHTTPServerTransport` (stateless,
`enableJsonResponse`) on `Bun.serve`.

- It calls `x402ResourceServer(fac).register("stellar:testnet", new ExactStellarScheme())`, then `await rs.initialize()`,

- `paid_quote` is registered through `createPaymentWrapper(rs, { accepts, resource: { url: "mcp://tool/paid_quote" } })`.

### 5c. Pocket model: pull, then pay from `G(K)` (two-step receipt)

`client/pocket.ts` with `lib/pocket.ts`.

- **Pocket creation, in one relayer transaction**: `BeginSponsoringFutureReserves(K)` → `CreateAccount(K, 0 XLM)` →
  `ChangeTrust(USDC)` (source K) → `EndSponsoringFutureReserves` (source K). It is signed by the relayer and K, costs a
  400-stroop fee, and takes about 5 s.
- **Result**: `G(K)` has `xlm 0.0000000`, `num_sponsored 3` (2 for the account entry, 1 for the trustline) and
  `subentries 1`. The relayer's `num_sponsoring` rose by 3.
- **Pull**: x402's `onBeforePaymentCreation` hook (`attachPocketPull`) fires after the 402 is parsed and before
  anything is signed.
  - It pulls the shortfall (price minus what `G(K)` holds; that is exactly the price when the pocket is empty) with a
    Soroban SAC `transfer(funder → G(K))`.
  - It waits for confirmation, then lets the stock client sign as `G(K)`.
  - In the build, the funder transfer is replaced by S1's delegated transfer from the smart account, signed by K under
    the spending-limit rule with the relayer as source.

**XLM for the pocket.** The base reserve is 5,000,000 stroops (0.5 XLM).

- An unsponsored `G(K)` needs (2 + 1 trustline) × 0.5 = **1.5 XLM** locked, and nothing for fees: the facilitator pays
  the settlement, and the relayer is the source of the pull.
- With sponsorship the same 1.5 XLM is locked in the relayer instead, and `G(K)` holds 0.
- **Recommendation: sponsor.** It is 4 operations and one extra signature from a key the server already holds. The
  pocket never holds XLM, so a leaked K can take no XLM. "The relayer paid everything" stays literally true. Close
  returns the reserve to the relayer.
- Plain funding with 1.5 XLM would also be recoverable through `AccountMerge`, so the cost is the same either way.
  Sponsorship wins on cleanliness, not on cost.

## Recommendation for the build

1. **Facilitator for the demo: x402.org**, with OZ Channels configured as the fallback. Both run the stock reference
   `exact` Stellar code and settled every payment we sent: x402.org 10/10, OZ 3/3, 0 errors, 11:39–12:00 UTC.
   - x402.org needs no key and settled faster (1.5–6.7 s against 6.6–6.8 s).
   - OZ needs a Bearer key, a Worker secret generated at `/testnet/gen`.
   - Keep both URLs in config and probe `/supported` when the demo starts.
   - The pocket model keeps every payment a plain G-account transfer, about 21–22k stroops, so neither ceiling matters
     (x402.org about 50k simulated; OZ 1M declared).
2. **Pay from the pocket, not from the C-account.** Each connection grant gets `K` (already the S1 connection signer) and
   a sponsored `G(K)` created when the grant is installed. The C-account's spending-limit policy meters the pull; the
   seller only ever sees a normal G payer. No fork, no own facilitator, no PR #3399/#3860 dependency.
3. **`paid_resource_fetch(url, idempotency_key)`**:
   1. Look up the intent by idempotency key. If a receipt exists, return it and do nothing else.
   2. `GET url`. On 402, `x402HTTPClient.getPaymentRequiredResponse` reads the terms from the `PAYMENT-REQUIRED` header
      (the body is `{}`).
   3. `x402Client` with `createEd25519Signer(K)` and `setSpendControls({ maxAmountPerPayment })` as the per-payment belt.
   4. `onBeforePaymentCreation` does the grant work:
      - check asset = USDC SAC, network, and price ≤ grant remaining, with the reservation in the Durable Object;
      - if the price does not fit, return `{ abort: true }`, which maps to `requires_approval` (owner lane);
      - otherwise pull the shortfall with S1's delegated transfer C → `G(K)`, with the relayer as source;
      - await confirmation and store the pull tx.
   5. Attach `payment-identifier` = the intent id. Retry with `PAYMENT-SIGNATURE`.
   6. `getPaymentSettleResponse` → `{ success, transaction, payer, network }`. Return content and receipt **only when
      `success`** (acceptance test 7).
4. **`paid_mcp_call`**: use the same `x402Client` and hooks, wrapped by `wrapMCPClientWithPayment(mcp, x402Client, { autoPayment: true, onPaymentRequested })`.
   - `onPaymentRequested` is the grant check: it returns false → `requires_approval` with no signature.
   - `onBeforePaymentCreation` does the pull.
   - The receipt is `x402MCPToolCallResult.paymentResponse`, which equals `result._meta["x402/payment-response"]`.
5. **Receipt shape** (store both hashes; the explorer links prove each step):
   `{ intent_id, grant_id, lane: "autonomous", resource, amount, asset, payTo, pull: { tx, ledger, from: C…, to: G(K), fee_stroops, fee_payer: relayer }, settlement: { tx, ledger, payer: G(K), facilitator_url, fee_stroops, fee_payer: facilitator }, payment_identifier }`.
6. **Idempotency must live in our service, before the pull.** Seller-side `payment-identifier` dedup prevents a second
   settlement but not a second pull: the replay re-pulled 0.10 (call 2 above), and the onchain policy counts pulls.
   - Pull the shortfall, not the price, so any float is reused.
   - On revoke, sweep `G(K)` back to the C-account with a Soroban SAC transfer (relayer as source, K signs the address
     auth entry), then close the pocket.
7. **Sellers we run**: the seller must cache by payment id itself (`seller/index.ts`, about 40 lines); `@x402/hono` 2.28.0
   does not. The x402 MCP wrapper works as is.
8. **Froggy `packages/payments`**: nothing from it was needed. `@x402/core`'s `x402Client` and `x402HTTPClient` already
   cover requirement selection, header encoding and settle-response decoding for Stellar. Research Q6's reuse notes still
   apply if the Worker wants Effect-shaped wrappers.

## Open risks

1. **x402.org settled 1.5 s → 6.7 s, OZ about 6.7 s.** With the pull (about 5 s, one ledger), a pocket purchase takes
   **9.6–13.5 s** end to end, and MCP hosts must not time out first. Option: keep a small float in `G(K)` (pull 2–3
   prices at a time). The policy still counts it, but the float sits outside the C-account until used or swept.
2. **A signed but unsettled payload is live until its expiry ledger** (about 12 ledgers for `maxTimeoutSeconds: 60`). In
   the dedup run the client signed a second payload that the seller's cache never settled; the seller could have
   submitted it.
   - In the pocket model a stray payload can settle only if `G(K)` holds funds, so exposure is at most one price for 60 s.
   - Service-side idempotency before the 402 negotiation avoids creating the stray payload in the first place.
3. **A pull without a settlement consumes allowance.** If the seller or facilitator fails after the pull, the money is
   in `G(K)`, not lost. The grant's "remaining" should therefore read (policy remaining + pocket float). On revoke the
   float must be swept back to the C-account.
4. **Facilitator availability.** One morning of probes, no failures, no SLA. x402.org returns only generic
   `invalid_exact_stellar_payload_simulation_failed` reasons. OZ needs a key; the testnet key endpoint is open today.
5. **SDK split.** Everything here ran on stellar-sdk 16.4.1. `@x402/stellar` 2.28.0 needs `^16`. The Worker must not
   pass XDR objects between a 16.x and a 17.x copy. This was not tested in workerd.
6. **The pull's own cost is ours, and it is not always small.** S1's demo log
   (`spikes/s1/out/demo-run1.txt`) shows delegated connection transfers under the spending-limit policy at **14,200,403 and
   14,200,414 stroops** (about 1.42 XLM each, claim 3: baee7248…, fa791499…) and 23,873 for a later one (e1711625…).
   - In the pocket model the relayer pays this, so no facilitator ceiling applies.
   - It does affect relayer funding, and S1 or S5 should explain the 14.2M case.
   - A C-account payer going straight through a facilitator would hit either ceiling at that cost.
7. **x402.org's advertised signers are its tx source and fee-bump account. OZ's advertised signer `GCNJB6V5…` appears in
   neither of OZ's two settlements**: it used channel accounts with fee bump `GA6THKUY…H7TL`. Do not allowlist facilitator
   addresses from `/supported`.
