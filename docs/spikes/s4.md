Deployed: **`https://hm26-s4-mcp.kristjan-grm11775.workers.dev/mcp`**. It runs on account `bceaeae4…` (Kristjan.grm1,

## Question

Which OAuth implementation gets a remote MCP server on Cloudflare Workers connected to real hosts fastest? Does the
`approval_url` round trip work? Does `@stellar/stellar-sdk` run inside the Worker?

**Answers:**

- **OAuth:** use `@cloudflare/workers-oauth-provider` **1.2.4** as one Worker (`OAuthProvider`) with DCR **and** CIMD
  switched on. A real Claude Code connected over **CIMD** with no registration step. Goblin's SDK connected over DCR.
- **Approval round trip:** it works. The tool result carries the link in plain text, the owner approves in a browser,
  and the agent polls `payment_status` until it reads `confirmed`. Claude Code relayed the URL verbatim.
- **Stellar SDK:** 16.4.1 and 17.3.0 both build and sign a transaction and call Soroban RPC in the deployed Worker.
  **Neither needs `nodejs_compat`.**

The one surprise: the box's `CLOUDFLARE_API_TOKEN` **has no Workers KV permission** (the KV API returns 401, code 10000,
on every account). So `OAUTH_KV` runs on a Durable Object-backed shim (`spikes/s4/src/kv-shim.ts`).

## What happened

### Claim 1: which OAuth implementation (decided in about 5 minutes)

**Choice: (a) `@cloudflare/workers-oauth-provider` 1.2.4.**

**Why not port Sidequest:** Sidequest's OAuth is 1,546 lines across `oauth.ts`, `oauth-setup.ts`, `oauth-refresh.ts`,
`oauth-validation.ts` and `mcp.ts`. It is wired to `AgentStore` from `@sidequest/board`, which runs over a Postgres
`Sql` handle, and to Sidequest's setup-scope and roles semantics. Porting it means replacing its storage and stripping
its domain before writing a single line of ours.

**Why the library:** it ships everything this spike needs:

- RFC 8414 and RFC 9728 metadata, and the 401 challenge
- DCR and CIMD
- PKCE S256, with S256 the only method accepted
- refresh-token rotation and RFC 7009 revocation
- RFC 9207 `iss` on the callback
- consent helpers: a `__Host-` cookie, a handle bound to the browser, frame-deny headers
- grant `props`, encrypted, that reach the API handler as `ctx.props`

It did not block at any point. The only extra work was the KV shim. Writing the Worker, deploying it and getting the first
green end-to-end run took about 25 minutes.

### Deploy and the KV permission

- The first `wrangler deploy` failed while provisioning `OAUTH_KV`:
  `A request to the Cloudflare API (/accounts/bceaeae…/storage/kv/namespaces) failed. Authentication error [code: 10000]`.
- A direct probe of the API with the same token gave these statuses:

  | Endpoint                             | `bceaeae…` (ours) | `b667fec…` (swarmm) |
  | ------------------------------------ | ----------------- | ------------------- |
  | `storage/kv/namespaces`              | **401**           | **401**             |
  | `workers/scripts`                    | 200               | 200                 |
  | `workers/subdomain`                  | 200               | 200                 |
  | `d1/database`                        | 200               | 200                 |
  | `workers/durable_objects/namespaces` | 200               | 200                 |

- **The fix:** `OAuthStore`, a SQLite Durable Object, implements the part of KV the library uses: `get` (text and json),
  `put` (with `expiration`, `expirationTtl` and `metadata`), `delete`, and `list` (prefix and cursor). I took that list
  from the 1.2.4 dist, which makes 19 `get`, 9 `put`, 6 `delete` and 7 `list` calls, all with string values. The Worker
  passes `{ ...env, OAUTH_KV: durableKv(env.OAUTH_STORE) }` into `provider.fetch`.
- **Side benefit:** reads are strongly consistent. Real KV can serve a stale miss for up to 60 s.

### Metadata and the 401 challenge (curl)

- `GET /.well-known/oauth-authorization-server` → **200**. It advertises:
  - `registration_endpoint`
  - `code_challenge_methods_supported: ["S256"]`
  - `token_endpoint_auth_methods_supported: ["client_secret_basic","client_secret_post","none","private_key_jwt"]`
  - `client_id_metadata_document_supported: true`
  - `authorization_response_iss_parameter_supported: true`
  - `scopes_supported: ["wallet","offline_access"]`
  - `protected_resources: [".../mcp"]`
- `GET /.well-known/oauth-protected-resource/mcp` → **200**:
  `{"resource":".../mcp","authorization_servers":["https://hm26-s4-mcp.kristjan-grm11775.workers.dev"],"scopes_supported":["wallet"],"bearer_methods_supported":["header"]}`.
- `POST /mcp` without a token → **401**, with
  `www-authenticate: Bearer realm="OAuth", resource_metadata="https://…/.well-known/oauth-protected-resource/mcp", scope="wallet"`.
  With a bogus bearer → **401** with `error="invalid_token"`.

### Claim 6: `@stellar/stellar-sdk` in the deployed Worker (`/api/probe`)

Each run builds and signs a testnet payment offline, verifies the signature, then calls Soroban RPC `getLatestLedger`
on `https://soroban-testnet.stellar.org` from the Worker. The offline transaction has a `Keypair.random()` source,
sequence 0, one `payment` op of 1 XLM and the testnet passphrase.

| SDK    | Flags           | Envelope hash                                                      | Signature | RPC ledger / protocol | RPC ms |
| ------ | --------------- | ------------------------------------------------------------------ | --------- | --------------------- | ------ |
| 17.3.0 | none            | `5f9175f5e07b50e8b10722879993342ec43461de2cf32fd59a01216c81fe4e5c` | verifies  | 5380962 / 29          | 674    |
| 16.4.1 | none            | `0f6b12971770d134437b08c3b3f5d391ab554db153f9d75abaee64b5901873c0` | verifies  | 5380962 / 29          | 501    |
| 17.3.0 | `nodejs_compat` | `a22b117b8f10572d94920d5427fc3625941c9c33d47811651d8340cf3091db27` | verifies  | 5381009 / 29          | 531    |
| 16.4.1 | `nodejs_compat` | `875704f921e3ab54d8080186f2af98480a7676264ec3f835defd108e812b132d` | verifies  | 5381010 / 29          | 660    |

These are offline envelopes with unfunded sources, so they were never submitted and have no explorer links. The
evidence is `evidence/probe-{16,17}{,-nodejs-compat}.json`.

- **No polyfill and no `nodejs_compat` needed for either version.** For 16.4.1, wrangler's esbuild bundles the npm
  `buffer` package that stellar-base depends on, so `tx.hash()` is that polyfill's `Buffer`. This corrects the research
  note that 16.4.1 needs `nodejs_compat`: it works with or without the flag. The foundation already reads a contract
  with 16.4.1 locally.
- **17.x API breaks** that the probe hit:
  - `tx.hash()` returns a `Uint8Array`, so `.toString('hex')` prints comma-separated decimals.
  - XDR structs expose plain properties: `tx.signatures[0].signature` is a field, not an accessor function. My first
    17.3.0 probe got Cloudflare error 1101, and `wrangler tail` showed
    `TypeError: tx.signatures[0].signature is not a function` at `src/probe.ts:16`.
  - Code written for 16 that hex-encodes hashes or walks XDR **silently breaks** on 17.
- `Date.now()` does not advance during CPU work on Workers, so a meaningful `build_sign_ms` cannot be measured
  in-Worker. Startup time is the wrangler figure in the table above.

## Recommendation for the build

1. **OAuth library:** `@cloudflare/workers-oauth-provider` 1.2.4, one Worker (`OAuthProvider`).
   - Settings: `apiRoute: '/mcp'`, `authorizeEndpoint: '/authorize'`, `tokenEndpoint: '/oauth/token'`,
     `clientRegistrationEndpoint: '/oauth/register'`, `clientIdMetadataDocumentEnabled: true` (plus the
     `global_fetch_strictly_public` flag), `scopesSupported: ['wallet', 'offline_access']`, `requiredScopes: ['wallet']`.
   - Keep **both DCR and CIMD**: Claude (Code and web) uses CIMD, while Goblin and the MCP SDK clients use DCR.
   - `resourceMetadata.resource` must be the exact public `…/mcp` URL for each stage. The spike builds one provider per
     request origin (`providerFor(origin)`) so localhost, workers.dev and a custom domain all work.
2. **Storage:** pick one before the build starts.
   - (a) Ask Kristjan for a token with **Workers KV Storage: Edit**. Alchemy needs that permission to create the
     namespace too.
   - (b) Keep `kv-shim.ts`: proven on every flow above and strongly consistent, but a single global Durable Object.
   - I would keep (b) for the hackathon. It removes one permission dependency and one eventual-consistency failure mode.
3. **The consent page is the grant ceremony.** It must show:
   - the client name. For a CIMD client, "**Published by &lt;domain&gt;**" (`describeConsent().clientDomain`); for a DCR
     client, "registered itself; its name is not verified".
   - the redirect host, plus a warning when it is loopback
   - the wallet (name and network)
   - **allowance amount + asset + expiry**, editable, with "Larger payments need your passkey"
   - the owner's sign-in (the passkey) and Allow/Deny
   - The passkey assertion that installs the onchain context rule belongs on this page's POST, before
     `completeAuthorization`.
   - Escape all client metadata, and send `beginConsent()`'s headers (frame-deny, binding cookie).
4. **How tokens map to the connection and the grant:**
   - One consent → `completeAuthorization({ userId: owner_id, props, metadata, revokeExistingGrants: false })` →
     **one OAuth grant = one connection = one spending grant**.
   - `props`, encrypted and delivered as `ctx.props` on every `/mcp` call, carries `owner_id`, `wallet_id`,
     `connection_id` (a fresh UUID), `client_id`, `client_name` and
     `grant {grant_id, allowance, valid_until, signer_key_id}`.
   - `metadata` is plaintext and listable: `connection_id`, `client_name`, `grant_id`, `allowance`, `valid_until`.
   - Refresh keeps `props` (same `connection_id`, proven).
   - **Never key anything on `client_id`.** CIMD client ids are shared by every Claude user, and one person can hold
     several connections from the same client.
   - Mutable grant state (spent, reserved, revoked) lives in D1/DO under `grant_id`, not in `props`. `props` is a
     snapshot from consent time.
5. **Revoke = `env.OAUTH_PROVIDER.revokeGrant(grantId, ownerId)`, plus the service-side grant flag, plus onchain rule removal.**
   - RFC 7009 revocation of one access token leaves the refresh token alive (200).
   - A refresh does not kill the previous access token (200 until its TTL), so keep `accessTokenTTL` short (1 h here).
   - **Build the Connections list from our own records.** `listUserGrants` also returns grants whose code was never
     exchanged; they live for 600 s (visible in `connections-revoked.png`).
6. **Approval link:** return it **twice**: as a plain sentence first in `content` ("Ask the user to open … then call
   `payment_status` with payment_id …") and inside `structuredContent`.
   - Claude Code relayed it verbatim and polled correctly.
   - Claude Code declares `elicitation.url`. But a stateless JSON-response server cannot send a mid-call
     `elicitation/create`: the answer would reach a fresh instance that has no record of the request.
   - URL-mode elicitation therefore needs sessions (an `McpAgent` Durable Object, or SSE responses plus a stateful
     transport), or the 2026 `input_required` result that Goblin implements (ADR 0042). **Optional polish, not on the
     critical path.**
7. **MCP transport:** stateless `WebStandardStreamableHTTPServerTransport` with `enableJsonResponse: true`, POST only,
   GET → 405. Every client tried (SDK v2 and Claude Code) handles the 405. Add `annotations.readOnlyHint` on reads.
8. **stellar-sdk:** use **16.4.1**, as the coordinator decided for the smart-account kits. It works on Workers without
   any flag and is 2.2× smaller than 17.3.0 (150 KiB vs 244 KiB gzip). If any package pulls 17.x in, watch for the
   `Uint8Array` hash and the plain-property XDR shown above.
9. **Local dev works:** the full e2e (66 assertions) passes against `wrangler dev` on `http://localhost:8799`. The
   provider accepts `http` loopback resources, and Chromium keeps the `__Host-` consent cookie on localhost. Expect the
   same from `alchemy dev`, which runs the same workerd.

## Open risks

- **claude.ai, Goblin and ChatGPT have not been connected live.** Only Claude Code was. Kristjan should run
  `s4-connect.md` (Claude first) before the 16:00 step back. Claude's backend allows 10 s per OAuth endpoint. Our
  metadata answers in < 0.5 s, and consent rendering includes a CIMD fetch of claude.ai's document.
- **The KV shim** covers exactly the calls 1.2.4 makes. A library upgrade that calls, for example, `getWithMetadata`
  fails loudly (`durableKv` throws on unsupported types), not silently. It is one global DO, which is fine at demo
  scale.
- **workers-oauth-provider 1.2.4 is three days old** (2026-10-22). Pin it exactly.
- **ChatGPT:** its policy prohibits crypto transfers, plan gating is unclear, and its CIMD URL is unknown. DCR is
  advertised, so dev mode should register itself.
- **The dev password stands in for owner sign-in.** In the build, the passkey replaces it on all three pages (consent,
  approval, connections), and the approval POST must verify a WebAuthn assertion over the intent's auth digest.
- **Fake settlement:** `payment_status` → `confirmed` comes from a timer, not a transaction. The real state machine is
  S1/S5's job.
- The 405 on GET `/mcp` is fine for every client tried. A host that insists on a standalone SSE stream would need the
  stateful transport.
