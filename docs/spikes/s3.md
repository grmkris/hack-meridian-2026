# S3 · CAP-73 recipient onboarding in one invocation: results

Status: **PASS** on all claims, 2026-10-25 11:30–11:50 UTC, Stellar testnet (protocol 29). Author: S3 spike agent.

## Question

Can a small Soroban router call the USDC Stellar Asset Contract's CAP-73 `trust` for a recipient and then
`transfer(sender, recipient, amount)` in **one** transaction? The recipient is a classic `G…` account with no USDC
trustline and authorizes only the trustline. The sender authorizes only the transfer. A third account (the relayer) is
the transaction source and pays the fee.

**Answer: yes.** Each party signs one auth entry whose root is exactly one SAC call. The catch is in the first
simulation: it must use `authMode: 'record_allow_nonroot'`, because the default `record` mode rejects the call.

## What happened

### 1. The SAC function is `trust(addr: Address)`

`stellar contract info interface` on the USDC SAC lists `fn trust(env: soroban_sdk::Env, addr: soroban_sdk::Address);`
next to the usual SEP-41 functions. Note that `transfer` takes `to: soroban_sdk::MuxedAddress` (CAP-67). Passing an
`Address` works because the SDK provides `From<&Address> for MuxedAddress`. soroban-sdk 29.0.1 declares `trust` on
`token::StellarAssetInterface`, so `token::StellarAssetClient::trust(&addr)` is available in contracts. Its doc comment
says: a no-op for C-addresses and for an existing trustline; `addr.require_auth()` only when a trustline is actually
created. The trustline it creates has limit i64::MAX: Horizon shows `"limit":"922337203685.4775807"` for
`recipient_direct`.

### 2. A recipient without a trustline: `balance` errors, it does not return 0

```text
❌ error: transaction simulation failed: HostError: Error(Contract, #13)
   0: [Diagnostic Event] contract:CBIELTK6…DAMA, topics:[error, Error(Contract, #13)],
      data:["trustline entry is missing for account", GAPKNR7GOARUP3U3TM6I3ZFHGY5O6JQF7AY3NRBV2GVGX2FC3ZIMNDYX]
```

Horizon showed the same account with only `native` 10000.0000000 and `subentry_count: 0`. **For the build:**
readiness detection can treat SAC `Error(Contract, #13)` on `balance` as `trustline_required` (or read Horizon's
balances).

### 3. The router contract and its unit tests

`spikes/s3/contracts/onboard/src/lib.rs` is the whole contract:

```rust
pub fn pay_and_trust(env: Env, sender: Address, recipient: Address, token: Address, amount: i128) {
    token::StellarAssetClient::new(&env, &token).trust(&recipient);
    token::TokenClient::new(&env, &token).transfer(&sender, &recipient, &amount);
}
```

The router calls `require_auth` on nobody, on purpose. Five unit tests pass under `heavy cargo test`, about 30 minutes of
work. The tests create a real classic G account ledger entry through `env.host().add_ledger_entry`, because
`Address::generate` only makes C-addresses, for which `trust` is a no-op. The tests:

- `recipient_without_trustline_reads_as_error`: `try_balance` on the G recipient errors.
- `default_recording_auth_rejects_non_root_trust_auth`: `mock_all_auths()` fails with
  `"[recording authorization only] encountered authorization not tied to the root contract invocation for an address. Use require_auth() in the top invocation or enable non-root authorization."`
  This is the same failure that `simulateTransaction` shows in its default mode (see 4).
- `trust_and_transfer_in_one_invocation_with_two_narrow_auths`: with `mock_all_auths_allowing_non_root_auth()`,
  `env.auths()` is exactly `[(recipient, USDC.trust(recipient)), (sender, USDC.transfer(sender, recipient, 20000000))]`.
  Neither tree has sub-invocations, and the router does not appear in either.
- `without_recipient_auth_the_whole_invocation_fails`: with only the sender's `MockAuth`, the call fails and nothing moves.
- `existing_trustline_makes_trust_a_no_op_that_needs_no_recipient_auth`: the second payment with only the sender's
  `MockAuth` passes, and `env.auths().len() == 1`.

Test gotcha: `env.mock_auths(&[MockAuth { address: <G account>, … }])` panics with `"not a contract address"`. It only
mocks C-addresses, so G-address auth in tests needs `mock_all_auths_allowing_non_root_auth`.

### 4. Positive run on testnet: trust + transfer in one transaction, three parties

`bun src/onboard.ts` (output, abridged):

```text

[sim authMode=record_allow_nonroot] ok, 2 auth entries, minResourceFee=92952250
  entry { who: "GAPKNR7G…MNDYX", call: "CBIELTK6…DAMA.trust",    subInvocations: 0 }
  entry { who: "GAIAD7IE…D53XQ", call: "CBIELTK6…DAMA.transfer", subInvocations: 0 }
  signed by recipient (valid until ledger 5381059)
  signed by sender (valid until ledger 5381059)
[sim enforce, signed] ok, minResourceFee=45220
result: SUCCESS  feeCharged=37237 stroops (paid by relayer)
recipient after: USDC=5.0000000 XLM=10000.0000000

```

**PASS:**
[d931ec2674e48d0f4edb21072937edbc7a21bf7d86cd735005d3c8b599fa4f8e](https://stellar.expert/explorer/testnet/tx/d931ec2674e48d0f4edb21072937edbc7a21bf7d86cd735005d3c8b599fa4f8e)
(ledger 5380940). The recipient got the trustline and 5 USDC in one transaction. Its XLM stayed at exactly
10000.0000000 because the relayer paid the whole fee: 37,237 stroops, about 0.0037 XLM.

The sequence that worked:

1. Simulate with `authMode: 'record_allow_nonroot'`.
2. Call `authorizeEntry(entry, keypair, latestLedger + N, passphrase)` once per signer.
3. Rebuild the transaction with the signed entries.
4. Re-simulate with `'enforce'`.
5. Call `rpc.assembleTransaction`. It keeps auth entries that are already present.
6. The relayer signs the envelope, then `sendTransaction` and `pollTransaction`.

Two simulation facts the build must handle:

- **The default `simulateTransaction` (`record`) fails** with `Error(Auth, InvalidAction)` for every router call
  here. That includes the case where the trustline already exists, because the sender's `transfer` auth is non-root
  too. Pass `authMode: 'record_allow_nonroot'` (SDK 17.3.0: the third argument of `simulateTransaction`).
- **Do not submit with the record-mode simulation's fees.** It reports `minResourceFee` of about 46.5 M stroops
  (about 4.65 XLM) per address auth entry: 92,952,250 with two entries, 46,481,411 with one. Leeway is not the cause;
  without it the figure was 46,480,826. The enforce re-simulation after signing gives 45,220. The negative test below
  was assembled from the record simulation and carried `max_fee` 93,052,250 (9.3 XLM), although only 15,227 was
  charged. The likely cause is that the rent of the nonce entries is estimated before any expiration is known; this is
  **UNVERIFIED**. The relayer would otherwise need about 9 XLM spare per submission.

**Reserve.** The recipient needs **0.5 XLM spare** above its current minimum balance. A fresh account with no other
subentries needs **1.5 XLM in total**, and the recipient pays nothing else:

- `recipient_1xlm` was created with exactly 1.0 XLM
  ([b310c65d…](https://stellar.expert/explorer/testnet/tx/b310c65d4e4afa7f64f1c78ad0d15c8ca164e864f3f0e5f8639630dd8b089840)).
  Simulation failed with `Error(Contract, #14)` and the SAC diagnostic
  `"account has insufficient reserve for new trustline"`, raised inside `trust` under the router.
- `recipient_15xlm` was created with exactly 1.5 XLM
  ([c8c86363…](https://stellar.expert/explorer/testnet/tx/c8c86363601d4163aa35158a4c4e334569a23e0dbd7d568369b5c3e8368f0d01)).
  The payment succeeded:
  [4b9e7b9421da761677de3fb70af38188206834db9dc6ec0988410baeb98f9b08](https://stellar.expert/explorer/testnet/tx/4b9e7b9421da761677de3fb70af38188206834db9dc6ec0988410baeb98f9b08).
  The account ended at `USDC=5.0000000 XLM=1.5000000`.

`trust` cannot sponsor the reserve. If the product wants to top up a nearly empty recipient, the research doc notes
that an XLM SAC `transfer` can fund it from a third party. That is **not tested here**.

### 5. Negative and edge cases

**No recipient signature, so the whole invocation fails.** The run was
`bun src/onboard.ts --recipient recipient_neg --omit-recipient`. The recipient's entry is dropped and the sender's
entry is signed. The enforce re-simulation already refuses:

```text
HostError: Error(Auth, InvalidAction)
 2: contract:CBIELTK6…DAMA, topics:[error, Error(Auth, InvalidAction)],
    data:["Unauthorized function call for address", GBCXACZSRGHDGT3QB3CYAIL44EVQM7XJOFUXMSW3SSNC6GGIH6XGCE7A]
 1: contract:CCLFB4I4…PGN4, data:["contract call failed", trust, [GBCXACZS…CE7A]]
```

The run then submitted anyway, using the record-mode footprint, to get an onchain rejection:
[f380d185f4736fe40a5b4d0bed8bcfd8ba166674726211a4ff7c4fe5fd40ea00](https://stellar.expert/explorer/testnet/tx/f380d185f4736fe40a5b4d0bed8bcfd8ba166674726211a4ff7c4fe5fd40ea00).
The result was `tx_failed / invoke_host_function: trapped` with the same `"Unauthorized function call for address"`
diagnostic. Nothing moved: the sender kept its 15 USDC and the recipient still has no trustline. The relayer paid
15,227 stroops for the failure.

**Recipient already has the trustline, so the call is idempotent.** The run was `--recipient recipient --amount 10000000`
on the account from step 4. Simulation returns **one** entry (the sender's); `trust` is a no-op and asks for no auth.
[6816fe2c96062e29ce1c8d0a09e66521f7f8c725c09c4092c7d8ed81037dc957](https://stellar.expert/explorer/testnet/tx/6816fe2c96062e29ce1c8d0a09e66521f7f8c725c09c4092c7d8ed81037dc957)
succeeded: the recipient went from 5 to 6 USDC for 21,213 stroops. **The router is therefore safe to use for every
payment to a G address**, not only first payments.

**A pre-signed recipient entry that ends up unused does not fail the tx.** This answers an open question from the
research doc. The run was `--recipient recipient_stale --trust-first`. Both entries were signed, then the recipient
added the trustline itself with a classic `ChangeTrust`
([0eb919ae…](https://stellar.expert/explorer/testnet/tx/0eb919aede89b8e8187aeffd891c9fb552f5ac99c37acf793c40e05504f5b56d)),
then the transaction was submitted with both signed entries:
[cd05901957708c39033c1710b1a33c655cb1b721ebffc82fd3601bc1d49570ad](https://stellar.expert/explorer/testnet/tx/cd05901957708c39033c1710b1a33c655cb1b721ebffc82fd3601bc1d49570ad)
succeeded. So an acceptance link that the recipient signed does not break if they add the trustline in their wallet
before we execute.

### 6. Is `trust` reachable from the tools?

- **`stellar contract invoke … -- trust --addr G…`**: yes, per the research doc
  ([6cdd4728…](https://stellar.expert/explorer/testnet/tx/6cdd472809602437f95327c80cef5368291e839edbf1abca55b2d583de1334a4)).
  The interface printout above lists it.
- **SDK `new Contract(USDC_SAC).call('trust', addr)`**: yes. `bun src/trust-direct.ts` (default `record` mode, since
  the auth is root-level here):
  [a13efe602d189e1362470ce5eb5633eea127652861c72289fe53bddf2952bc16](https://stellar.expert/explorer/testnet/tx/a13efe602d189e1362470ce5eb5633eea127652861c72289fe53bddf2952bc16).
- **SDK `contract.Client.from({ contractId: USDC_SAC })`: no `trust` method.** For a Stellar Asset executable, SDK
  17.3.0 loads its bundled `bindings/sac-spec.js`. That spec decodes to no `trust` string; it does have
  `transfer_from` and `set_authorized`, so it predates CAP-73. The client's methods are
  `allowance, authorized, approve, balance, burn, burn_from, clawback, decimals, mint, name, set_admin, admin, set_authorized, symbol, transfer, transfer_from`.
  Use `Contract.call('trust', …)`.

### 7. How Freighter would sign the recipient's entry (acceptance-link flow)

1. The server builds `router.pay_and_trust(owner, carol, USDC, amount)` with the relayer as source. It simulates with
   `record_allow_nonroot` and stores Carol's unsigned entry: 220 base64 chars of `SorobanAuthorizationEntry` XDR, root
   `USDC.trust(carol)`. The link carries an id that points to that stored entry.
2. The link page connects Carol's wallet through Stellar Wallets Kit or `@stellar/freighter-api` and must check that the
   connected address equals `carol`.
3. The page calls `authorizeEntry(entry, walletSigner(signAuthEntry, carol, passphrase), validUntil, passphrase)`
   (`lib.ts`). The SDK then hands the wallet the **HashIdPreimage** XDR (base64) via `signAuthEntry(preimageXdr, { networkPassphrase, address })`.
   The wallet must return `{ signedAuthEntry: base64 ed25519 signature over sha256(preimage) }`.
4. This is exactly the contract that the SDK's own `AssembledTransaction.signAuthEntries` uses. Its type comment says
   "Matches signature of `signAuthEntry` from Freighter". So the recipient's wallet must support **`signAuthEntry`**,
   not just `signTransaction`.
5. The page POSTs the signed entry back. The server signs the owner's `transfer` entry (S1 connection key or passkey),
   re-simulates with `enforce`, and the relayer submits. Carol pays no fee and needs 0.5 XLM spare.
6. Proven on testnet with a Freighter-shaped stub (sha256 over the preimage XDR, ed25519, base64), entirely through
   `lib.ts`, including the XDR round trip through the "link":
   [9ba86256bf8e0722fc0e12d76c50e39e56f02f78cf85c7fe4ab721b60fc5ad6c](https://stellar.expert/explorer/testnet/tx/9ba86256bf8e0722fc0e12d76c50e39e56f02f78cf85c7fe4ab721b60fc5ad6c).
   A real browser Freighter popup was **not** exercised.
7. Link lifetime: the entry's `signatureExpirationLedger` is the link expiry. One hour (720 ledgers) cost 37,691
   stroops in total. One day (17,280 ledgers, applied to both entries)
   ([8e038c70…](https://stellar.expert/explorer/testnet/tx/8e038c7043193a83aad5d3fe69c598974b7c713ed5edeef730cddc12f6bd0115))
   cost 478,327 stroops (about 0.048 XLM, nonce-entry rent). Give only the recipient's entry the long expiry.

## Recommendation for the build

1. **Put the onboarding router in the demo (Unlocked).** Use it for **every** payment to a G address. With an
   existing trustline it costs nothing extra and needs only the sender's entry, so the payment path does not need two
   variants. The contract is 7 lines; copy `spikes/s3/contracts/onboard` into `contracts/` and deploy it per stage.
2. **Keep the router auth-free**, so it never calls `sender.require_auth()`. The sender's entry is then a plain
   `USDC.transfer(sender, recipient, amount)` with no router above it, exactly the context that S1's
   `CallContract(USDC_SAC)` + spending-limit rule matches. The unit test shows a C-address sender gets exactly that tree.
   Adding `sender.require_auth()` in the router would re-root the sender's tree at the router and miss that rule.
3. **Simulation recipe:** first simulate with `record_allow_nonroot`, sign each entry, re-simulate with `enforce`, then
   `assembleTransaction`. Never submit with the first simulation's fee. Port `spikes/s3/client/src/lib.ts`.
4. **Readiness:** SAC `balance` → `Error(Contract, #13)` means `trustline_required`. Also show "needs 0.5 XLM spare"
   when the recipient's available XLM is below minimum balance + 0.5 (Horizon `balances` + `subentry_count`). Below
   that, the call fails at simulation with `Error(Contract, #14)`; surface it as "recipient must add 0.5 XLM".
5. **Acceptance link:** store the unsigned recipient entry server-side and sign it in the browser with `signAuthEntry`
   (Wallets Kit / Freighter). Give it about a 1-day `signatureExpirationLedger` and a short one for the sender's entry.
   If the recipient adds the trustline on their own meanwhile, nothing breaks (proven).
6. **SDK:** 17.3.0 works for all of this. Do not use `contract.Client.from` for the SAC's `trust`; use
   `Contract.call('trust', …)` or the router. Note the 17.x XDR is property-style: `op.body.invokeHostFunctionOp.hostFunction`,
   `resultXdr.feeCharged`, and `inspectAuthEntry` / `buildInvocationTree` to read entries.
7. **Demo USDC:** buy it on the testnet SDEX with `fund.ts` (about 1.15 XLM per USDC right now) instead of the 20 USDC
   / 2 h faucet.

## Open risks

- **The C-account sender through the router is not executed.** Every testnet sender here was a classic G. The OZ smart
  account's `__check_auth` should see the context `USDC.transfer`, as in a direct payment (unit test with a C sender:
  same tree). S5 or the build should run one `pay_and_trust` with S1's account and connection key.
- **A real Freighter `signAuthEntry` popup is not exercised.** Unchecked: whether Freighter shows a readable
  "trust USDC" description for a nested entry, and which other Wallets Kit modules implement `signAuthEntry` (some do
  not).
- **The recipient's entry is not bound to the payment.** It authorizes only `USDC.trust(carol)`, so anyone holding the
  link payload could submit it alone. Carol would get the trustline (0.5 XLM locked) without the payment. That is
  harmless and arguably what she asked for. If the product wants "I accept 10 USDC from Alice" to be cryptographic,
  the router can add `recipient.require_auth_for_args((sender, amount))`. Carol then signs `router.pay_and_trust` with
  `trust` beneath it. That variant is **not tested**, and it would require Carol's signature on every payment, not only
  the first.
- **Record-mode simulation fee:** about 4.65 XLM per entry. Its cause is unverified. Any code path that assembles from
  the first simulation will lock that much `max_fee`.
- The reserve top-up for recipients below 1.5 XLM is untested (XLM SAC `transfer` from the relayer in the same router
  call is plausible per CAP-73).
