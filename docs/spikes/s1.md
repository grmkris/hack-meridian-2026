# S1 · Smart account authority model: results

Status: **done, all 7 claims PASS**, 2026-10-25 11:31–11:59 UTC (well inside the 4 h box). Testnet only.

## Question

Can one OpenZeppelin smart account on testnet (the already-deployed WASM `1b5f4534…`, no Rust) have (a) a passkey-style
admin signer and (b) an Ed25519 **connection** signer limited by a context rule to USDC SAC `transfer` under the deployed
spending-limit policy (5 USDC total, window ≥ lifetime, `valid_until` ≈ 1 day)? Are over-limit, post-expiry and
post-revoke transfers **rejected onchain**, while a separate funded G account (our relayer, the "sponsor") is the
transaction source and fee payer?

**Answer: yes, all of it, with plain `@stellar/stellar-sdk` 16.4.1 and about 25 lines of AuthPayload code.** Smart
Account Kit was not needed at runtime. The fallbacks were not needed either.

## What happened

### The flow that works (every smart-account tx below)

1. Build `invokeHostFunction(contract.fn(args))` with source = sponsor, then `simulateTransaction` (record mode).
   This returns the unsigned auth entry for the C-account. On this RPC the credential type is
   **`sorobanCredentialsAddress` (V1), not ADDRESS_V2**. `authorizeEntry` handles both.
2. Call `authorizeEntry(entry, cb, latest+60, TESTNET)`. The callback gets `payload` and computes
   `digest = sha256(payload ‖ ScVal::Vec<u32>(ruleIds).toXDR())`. It returns
   `AuthPayload { context_rule_ids: [ruleId], signers: { Signer → sig bytes } }` as an ScMap, with keys sorted in host order.
   For Ed25519 the sig bytes are `kp.sign(digest)` (64 bytes).
3. **Re-simulate with the signed entries in `"enforce"` mode.** This runs `__check_auth`, the verifier and the policy.
   Policy rejections surface **here**, at the second simulation.
4. `rpc.assembleTransaction(signed, sim2)` keeps the signed auth. Rebuild from a freshly read sponsor sequence, then
   `tx.sign(sponsor)`, `sendTransaction` and poll `getTransaction`.

- **Re-simulation is required.** Submitting with the record-mode footprint fails onchain with
  `Error(Storage, ExceededLimit)` (resources were sized without `__check_auth`):
  [`bd14ea4e`](https://stellar.expert/explorer/testnet/tx/bd14ea4e568d05b4fd11fc52e4128ee672bdca3d1ef9d50913e735f949fa7f84),
  0.00087 XLM charged.
- **Timings, from 30 txs across 4 runs:**
  - record sim 125–510 ms
  - signing ≤ 9 ms (Ed25519 or software P-256)
  - enforce sim 140–510 ms
  - send → final 2.4–7.1 s (typically 3.5–4.7 s)
  - one delegated payment takes about **4–5 s end to end**. Ledgers close at exactly 5.00 s (1000 ledgers = 5000 s).

**The exact shape the approval page must produce.** It matches smart-account-kit 0.8.0's `kit.signAuthEntry`
(`dist/kit/webauthn-ops.js` and `auth-payload.js`), checked against the verifier source at `stellar-contracts@1e513890`:

- Challenge: `navigator.credentials.get({ publicKey: { challenge: digest, rpId, allowCredentials:[{id: credId,
  type:'public-key'}], userVerification: 'required' } })`, where
  `digest = sha256(sha256(HashIdPreimage(entry, expiration)) ‖ ScVal::Vec<u32>([0]).toXDR())`.
  The browser writes `clientDataJSON.challenge = base64url(digest)`: 43 chars, no padding, exactly what the verifier
  compares.
- What the verifier checks:
  - `type == "webauthn.get"`
  - the challenge
  - flags: UP (0x01) and UV (0x04) are set, and BS is never set without BE
  - `secp256r1_verify(pubkey, sha256(authenticatorData ‖ sha256(clientDataJSON)), r‖s)`
  - `clientDataJSON` is at most 1024 bytes
  - It does **not** check the rpId hash or the origin. The browser binds the passkey to the rpId.
- `AuthPayload.signers[External(WEBAUTHN_VERIFIER, pubkey65 ‖ credId)]` holds
  `ScMap{ authenticator_data: Bytes, client_data: Bytes, signature: Bytes(64) }.toXDR()`. Keys are in this order.
  `signature` is DER → raw `r‖s` with **low-s** (`s > n/2 ⇒ n − s`). The signer key must be the exact stored
  `key_data`, credential id included.
- A recorded wire example (base64url) is in `spikes/s1/out/webauthn-run1.txt` ("approval-page wire payload").
  `authenticatorData` is 37 bytes (rpIdHash ‖ 0x05 ‖ counter).

## Recommendation for the build

**Signing stack.** Use `@stellar/stellar-sdk` 16.4.1 plus `spikes/s1/src/signer.ts` (copy it into the signer
boundary). There is no runtime dependency on Smart Account Kit for the server. On the approval page, SAK's
`kit.signAuthEntry` and our `webAuthnChallenge` + `authorizeWithWebAuthn` produce the same bytes. Ours needs only the
raw assertion, so the page can call `navigator.credentials.get` directly. Raw SDK was faster than SAK: zero time spent
fighting the AuthPayload, and no fallback needed.

**MCP server signs for a grant (autonomous lane).**

1. One Ed25519 keypair per grant (encrypted at rest). Its public key is both the rule signer and its own pocket G
   address, if we fund one.
2. Before signing, pre-check the remaining allowance:
   `remaining = spending_limit − cached_total_spent` from `readSpendingLimit(ruleId)`, after evicting entries with
   `ledger ≤ latest − period`. If `amount > remaining − reserved`, route to the owner lane. Never sign that.
3. Pay with `invokeAs(relayer, C, [connSigner], [ruleId], USDC_SAC, 'transfer', [C, to, amount])`.
4. If the enforce simulation fails, do not submit. Map the codes:
   - `#3221`: limit exhausted, so route to the owner
   - `#3002`: expired or the wrong rule
   - `#3000`: rule removed
   - `#3223`: not a `transfer`
   - `#10` (SAC): insufficient balance
5. The receipt is `getTransaction` SUCCESS (ledger + hash). Pass `amount` as an i128 in stroops (7 decimals).

**Owner approval link (passkey lane).**

1. On intent creation the backend runs `prepareInvocation(relayer, USDC_SAC, 'transfer', [C, to, amount],
   authValidForLedgers)`. Use about 400 ledgers for a 30-min intent (5 s/ledger plus a margin).
2. Store the unsigned entry XDR, `validUntilLedger`, and the digest from `webAuthnChallenge(entry, [0], validUntilLedger)`.
3. The page calls `credentials.get` with that digest as the challenge. It POSTs `{authenticatorData, clientDataJSON,
   signature}` (base64url).
4. The backend runs `authorizeWithWebAuthn` (it checks the challenge locally first), then `finalizeInvocation`. That
   re-reads the relayer sequence; proven with an interleaved tx. The digest binds recipient, amount, nonce and
   expiration, so the service cannot substitute anything.
5. Admin calls (`add_context_rule`, `remove_context_rule`) use the same path with the account itself as the contract.
   With SAK in the browser, pass `walletMutationHostFunction` or it refuses mutations on the generic path.

**Grant → rule mapping.**

- One grant = one context rule:
  - `CallContract(USDC_SAC)`
  - name ≤ 20 bytes, e.g. `g_<grantId>` truncated
  - `valid_until: Some(T_ledger)`
  - signers `[External(ED25519_VERIFIER, connPub32)]`
  - policies `{SPENDING_LIMIT: {period_ledgers, spending_limit}}`
- **Persist `ContextRule.id` from the `add_context_rule` return value.** Ids are monotonic and never reused: after
  removing 1, the next was 3. `get_context_rules_count` is the number of _live_ rules (it was 2 with ids {0, 2}), so
  never derive an id from it.
- The budget is keyed by `(account, rule_id)`, so a renewal is a **new rule** with a fresh budget, followed by
  `remove_context_rule(old)`.
- Revocation is `remove_context_rule` (owner passkey, about 0.0024 XLM). It also wipes the policy state.
- Expiry needs no tx. An expired rule lingers (counted, not deleted) until removed. Clean it up opportunistically.

**Period from a lifetime.**

- `L = ceil(lifetimeSeconds / 5)` ledgers
- `valid_until = latest + L`
- `period_ledgers = L + 720` (1 h margin; it must be ≥ `valid_until − install_ledger + 1`)

Why: a spend at ledger S is evicted at the first ledger C with `S ≤ C − period`, i.e. at `S + period` (confirmed: still
counted at S+14, gone by S+17 with period 15, matching the source). With `period > L`, nothing ages out before the rule
expires, so the grant is a non-replenishing "N USDC until T".

The rule is valid **through** `valid_until`. A past `valid_until` is refused (`PastValidUntil`, `#3005`, per the research doc; not exercised here),
so compute T from a fresh `getLatestLedger`. Show the expiry as ≈ wall time; the ledger number is authoritative.

**Fee budget for the relayer (testnet, measured).** Rent dominates:

| Operation                                                                                                   | XLM         |
| ----------------------------------------------------------------------------------------------------------- | ----------- |
| deploy account                                                                                              | ≈ 3.9–4.1   |
| first USDC into a new C (creates its balance entry)                                                         | ≈ 4.2       |
| first `add_context_rule`                                                                                    | ≈ 13.8      |
| later rules                                                                                                 | ≈ 3–7       |
| **first payment under each new rule** (extends rule, signer and policy entries from 7 to 30 days of TTL)    | **≈ 11–17** |
| **every further delegated payment** (the policy's history Vec grows by 80 bytes, rent prepaid for ~30 days) | **≈ 1.5**   |
| payment whose evictions keep the history size flat                                                          | ≈ 0.0024    |
| owner-lane payment on a warm account                                                                        | ≈ 0.002     |
| first passkey auth on a fresh account                                                                       | ≈ 8.4       |
| remove rule                                                                                                 | ≈ 0.0024    |
| a rejected tx forced onchain                                                                                | ≈ 0.001     |

The declared resource fee is about 15 % above the charge; the rest is refunded. One full lifecycle (deploy, fund, grant,
5 payments, revoke) costs **≈ 55 XLM**. On testnet that is fine (friendbot gives 10k per sponsor). Set the intent's fee
ceiling to ≥ 20 XLM for the first grant payment and ≥ 2 XLM after that, or simulation results will be refused.

**Concurrency.** One relayer G serializes on its sequence. The WebAuthn run used a second sponsor in parallel with no
issue. Use 2 or 3 relayers, or a queue in the Durable Object.

## Contradictions with `docs/research/smart-accounts.md`

1. The simulation returns **V1 `sorobanCredentialsAddress`** entries, not CAP-71 ADDRESS_V2. This is harmless, because
   `authorizeEntry` builds the matching preimage. Do not hard-code V2.
2. A conn key signing under rule 0 fails with **`#3002` UnvalidatedContext**, not `#3016` UnauthorizedSigner. We never
   saw `#3016`.
3. The research says to "read `get_context_rules_count` / the event" to learn a rule id. The count is the number of
   live rules and ids are monotonic, so use the `add_context_rule` return value.
4. The faucet is not needed: the SDEX sells Circle testnet USDC. We deployed with the SDK's `createCustomContract
   {wasmHash}`; the research's CLI `--wasm-hash` quirk does not apply.
5. The research does not mention fees. Rent makes the delegated lane cost ~1.5 XLM per payment on testnet, plus a
   ~11–17 XLM first payment per rule (see the fee table).
6. The constructor names rule 0 `"multisig"`. The research's other points held: the record-mode footprint is
   insufficient, the rolling window, `#3221`/`#3223`, expiry as `#3002`, the policy keyed by `(account, rule_id)`, and the
   WebAuthn key = pubkey65 ‖ credId.

## Open risks

1. **Delegated-lane rent on mainnet.** About 1.5 XLM per x402 payment plus about 15 XLM per grant's first payment would
   dwarf a 0.10 USDC purchase. The cause is the policy's growing history with 30-day TTL prepayment. This is fine for
   the testnet demo; flag it in the pitch's "next steps". Mitigations to explore: fewer, larger pulls into the pocket G
   (the pocket then pays x402 cheaply as a classic account), or a custom policy that stores only a running total.
2. **History cap.** 1000 entries per rule (`#3224`), so 1000 delegated payments per grant. That is fine for a demo.
3. **The deployed account lacks the GHSA-jpg9 fix.** Never add Delegated (G) signers. We use External only.
4. **The verifier ignores rpId and origin.** Security rests on the passkey being bound to our rpId by the browser, and on
   the challenge. A passkey for another site cannot sign for us because the pubkey differs. Do not reuse a credential
   across rpIds.
5. **SAK `connectWallet`** strictness with accounts not created by `createWallet` is still UNVERIFIED (not needed if the
   page uses raw `credentials.get` plus our helpers).
6. **Expired rules are not deleted.** Each lingers in storage until the owner removes it, which costs a passkey prompt.
   Batch the cleanup into the next owner action.
